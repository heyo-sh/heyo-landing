# Maintenance

Schedule a maintenance window before planned work so visitors know when to
expect disruption. While the window is in progress, checks still run, but
alerts and automatic incident updates for affected monitors are suppressed.
Maintenance windows are enabled by default.

```ts title="heyo-status.config.ts"
maintenance: { enabled: true },
```

Setting `maintenance.enabled: false` makes `/maintenance` and
`/admin/maintenance/*` return `404`. Windows no longer suppress alerts, and
the snapshot contains no upcoming or in-progress maintenance.

## Window fields and states

A window can be scheduled, in progress or completed. Its status follows the
clock rather than a separate job you have to run.

```ts
interface Maintenance {
  id: string;
  title: string;
  description: string;
  affectedMonitors: string[];
  scheduledStart: Date;
  scheduledEnd: Date;
  status: "scheduled" | "in-progress" | "completed";
  createdAt: Date;
}
```

The status is derived from the clock: reading upcoming windows refreshes
`scheduled` → `in-progress` → `completed` against the current time.
`scheduledEnd` must be after `scheduledStart`.

<Callout type="warning" title="Time changes status, not notifications">
  Reading a window after its start or end updates its stored status, but does
  not dispatch a <code>maintenance.starting</code> or
  <code>maintenance.completed</code> event. Lifecycle events are dispatched
  when a window is created or edited through the admin API, according to its
  resulting status. If you need an alert at the scheduled start or end,
  arrange an authenticated update at that time.
</Callout>

## Schedule a window

Create a window locally with the CLI, which talks directly to the database,
or use the admin API. HTTP management requires `adminToken` in the config;
load it from a private secret source.

<CodeBlockGroup defaultValue="heyo-status">
  <CodeBlock language="bash" title="heyo-status">
    {`heyo-status maintenance create --title "Database upgrade" --description "Read-only for about 30 minutes." --monitors "API,Dashboard" --start 2026-02-01T02:00:00Z --end 2026-02-01T03:00:00Z

heyo-status maintenance list`}
  </CodeBlock>
  <CodeBlock language="bash" title="curl">
    {`curl -X POST https://status.acme.com/api/heyo-status/admin/maintenance -H "authorization: Bearer $ADMIN_TOKEN" -H "content-type: application/json" -d '{"title":"Database upgrade","affectedMonitors":["API"],"scheduledStart":"2026-02-01T02:00:00Z","scheduledEnd":"2026-02-01T03:00:00Z"}'`}
  </CodeBlock>
</CodeBlockGroup>

## What happens to alerts

While a window is `in-progress`, the monitors it names are excluded from
`monitor.down`, `monitor.recovered` and `ssl.expiring` events, as well as
automatic incident creation and reconciliation. They are still checked and
results are stored, so uptime history shows what actually happened. An empty
`affectedMonitors` array suppresses alerts for every monitor.

<Callout type="info" title="Completed windows are not published">
  The snapshot and <code>GET /maintenance</code> include only scheduled and
  in-progress windows; completed ones are omitted.
</Callout>
